# SPEC — sim

Format: `- **ID** [principle][milestone] requirement — verification`

Kinds of verification: U = unit/property test, I = integration test (feed an event sequence to sim's state), E = terminal E2E (tmux), B = benchmark.
Test names start with the ID in lowercase (TREE-1 → `tree_1_...`). `sim/scripts/trace.sh` checks the mapping, like si's.
Sub-items that start with **Decided** record what was settled while implementing, with the principle that settled it.

Everything in si's SPEC holds for every file open in sim (P1). This file only adds.

## The tree panel

- **TREE-1** [P2][S1] `sim` without arguments, or `sim {dir}`, opens with the tree of that directory (the current one by default) in a panel on the left, focused. `sim {file}` (and `file:line[:col]`) opens the file with the panel closed. The panel is a third of the screen, at most 32 columns — I
  - **Decided** (P2): the panel is `min(32, w/3)` columns, followed by one blank column; narrower than 4 columns it is not drawn. A row is `indent 2 per depth`, then `▸ `/`▾ ` and `name/` for a directory, two spaces and `name` for a file, cut to the panel's width in columns (a wide char counts 2). The panel's cursor row is underlined while the panel has the focus (the terminal's cursor sits on it), and nothing else in the panel is styled. The status line is across the whole width: si's App cuts its status line to its own width, so when that line could be cut, or the command line is being typed, sim has the App render once more at the full width and takes the last row (the App's scroll state is put back: the first row, the skipped rows, centering and size; the command line's own scroll, `vi.off`, is kept by sim apart, because every update of the App renders its narrower frame and moves it, so the line scrolls at the width of the screen, VI-12).
  - **Decided** (P2): `sim {file}` reads the tree of the current directory too, for Ctrl-n later. A file opened from the tree or by `:e` is named by its path relative to the current directory when it lies below it, else by its absolute path; that name is what the status line shows and what the App, its snapshots and its saves use.
  - **Decided** (P1): a file name can hold anything, so the panel never sends one raw (SAFE-8's rule for names): control chars, bidirectional controls, U+200B and U+FEFF are shown as U+FFFD.
  - **Decided** (P2): with no file open the editor area shows five help lines (Ctrl-n tree, Enter open, Tab next file, q close, :qa quit all) in the secondary gray, and the status line is the selected path and `TREE` (the root when the panel has no focus). `q` in the text with no file open quits with 0; in the panel `q` closes the panel (TREE-4), so `q` twice leaves sim from the panel.
  - **Decided** (P4): the event loop needs the crates si's main.rs needs, because it is that loop for many files: crossterm (events, size), signal-hook (SIGTERM, SIGHUP) and unicode-width (columns), at si's versions and features, so the build gains no code. The snapshots go to si's directory (`$XDG_STATE_HOME/si`), so that si and sim recover each other's files. The tree and the file are read on the main thread like si does for `:e`; directory reads, saves and snapshots are threads. What the terminal sends goes through si's `term::convert_all` (Alt+x is Esc, then x; VI-9), and Shift-Tab, which si has no key for, is sim's.
  - **Decided** (P2): the status line keeps its state words, whatever the length of the path in front of them (a long `$TMPDIR`, a deep tree, an absolute path from `git commit`): the TREE line is the selected path (cut from the left, `…/dir/file`, at a `/` when one lets it fit, else inside a name) and `  TREE`, and the root shown alone when no file is open is cut the same way; `layout::tail` and `layout::stated` do it for sim's own lines, as si's status line does for its path. A message that names a directory names it as the panel does, below the root (`cannot read gone: Permission denied`), and `io::read_dir` answers with the reason alone.
- **TREE-2** [P2][S1] Ctrl-n opens and focuses the panel, or closes it when it already has focus (Neo-tree's key in the author's nvim). Esc in the panel gives the focus back to the text and leaves the panel open — U
  - **Decided** (P2): Ctrl-n is sim's in every mode (Insert and the command line too) and never reaches the App. With the panel open but not focused it focuses it. Opening the panel reads the root and every open directory again, so files made meanwhile show; the cursor stays on its entry.
- **TREE-3** [P2][S1] The order never changes: directories first, then files, each by name (case-insensitive, runs of digits compared as numbers). `.git` is not shown; everything else is, dotfiles included. Expanding or collapsing never moves what is above it, and the expansion stays as you left it — U
  - **Decided** (P2): the order of names is a total order, so it never depends on the order a listing arrives in. A name is read as tokens: a run of ASCII digits is one token that sorts where `0` would, by its value (any length, leading zeros ignored), anything else is one char, lowercased. Names are compared token by token; names equal that way (`a01` and `a1`, `A` and `a`) are ordered by their bytes. `.git` is hidden by name, whether it is a directory or a file (a worktree has a `.git` file).
  - **Decided** (P4): every node keeps the number of rows of its visible subtree, so a window of rows is found by skipping whole subtrees: the work is the rows asked for plus the siblings along the way, never the size of the tree. Rows carry their path relative to the root; an open directory whose listing has not arrived shows nothing below it.
- **TREE-4** [P2][S1] Keys in the panel: `j k` and the arrows move; `l`, Right and Enter expand a directory or open a file (the focus moves to the text); `h` and Left collapse a directory, or go to its parent; `gg G Ctrl-d Ctrl-u PageUp PageDown` move as in si; `-` collapses everything; `q` closes the panel — U
  - **Decided** (P2): the data side of the keys is in `tree.rs`: `row_of(path)` (none when a directory above it is closed), `parent_row(row)` (none at the top), `expand` (true when the listing is still to be read), `collapse`, `collapse_all` (the root stays open, listings that arrived are kept). The keys themselves come with the event loop.
  - **Decided** (P5): `l`, Right and Enter on an open directory do nothing. Ctrl-d and Ctrl-u move half the panel's height, PageUp and PageDown all of it; a `g` waits for a second one and any other key forgets it. `-` leaves the cursor on the top-level entry that held it. Tab and Shift-Tab (BUF-2) work from the panel too; Paste does nothing there.
- **TREE-5** [P4][S1] Directories are read in the background; entries appear when they arrive, without moving anything above them — I
  - **Decided** (P4): `insert_listing(dir, entries)` stores a listing whenever it arrives, whether or not `dir` is still expanded, and says false for a directory the tree does not know. A second listing for the same directory refreshes it: entries that stay keep their expansion and their own listing, a name that changes kind is a new entry. Reading a directory is `io::read_dir`: a symlink to a directory counts as a directory unless it leads to the directory itself or one above it (a loop); a link that cannot be followed is a file. Loops through two siblings are not detected: they cost one expansion each, never a walk. The background thread comes with the event loop.
  - **Decided** (P2): the cursor and the first row stay on their entries (found by path) whatever a listing puts above them. A directory that cannot be read stays open and empty, and the status line says why.

## Several files

- **BUF-1** [P1][S1] Each open file is a complete si App: its own undo, snapshots, watcher, proposals and saves. Opening a file that is already open switches to it — I
  - **Decided** (P1): sim's events and effects are si's, tagged with the id of the file they belong to (ids are never reused, so a late answer for a closed file is dropped). There is one save thread and one journal thread for all files, a watcher for each, and `Sim::update` gives every file's App the events si's loop would: ticks, signals, disk changes, save results. The shell starts watching before it reads, then looks for the snapshot a dead session left, and the first keys (`+cmd`, `file:line`) are typed after the recovery, as in si. The shell does for each file what si's main does for its one: the watcher's thread makes the hash of what it read (`Disk { hash }`, so no key waits for hashing, P3), and an App's `Effect::Watch` (asked for after every save's answer, PROP-1) replaces that file's watcher by one whose first read comes before the debounced ones.
  - **Decided** (P1): on si's M5 every disk read is numbered (PROP-1), per file, as in si's main: the number is taken from `file::seq()` when a read starts. A watcher's reads are numbered by `watch` itself (the first read of a new watcher, which follows every save's answer, included) and sim passes the number on in `Event::Disk`; `Effect::Open` (`:e!`, a reload) takes it before its read and carries it in `Event::Opened`; the save thread numbers each answer, `Saved` and `SaveConflict`, when the save is done. The first load of a file (`Opened`) is not numbered, as in si. Each App keeps the newest number it took in and drops an older read, so a read that began before a save's answer cannot undo it, in any file.
  - **Decided** (P1): on si's M4 the filters, the hook and the places hold per file. `Effect::Spawn` runs `sh -c` in its own process group, one running filter for each file at most (the App allows one), and its answer comes back as `Event::FilterDone` tagged with the file's id, so it finds its file wherever the user is; `Effect::Kill` stops that file's group; a closed file's group is stopped, and so are all groups at exit; an id that is not open drops the answer. `SI_ON_NORMAL` (VI-11) is given to every App (`app.hook`), and every App has the working directory (`app.cwd`). Where a file was closed (CLI-6) is looked up with the file (`Opened.place`) and given to the App as `Event::Place` unless keys were typed at startup (`+cmd`, `file:line`: for the first file only); `Effect::Open` of a reload asks the journal thread, whose answer is tagged with the id; `Effect::Remember` is a job of the journal thread, which reads the places again before it saves them. A signal, `:cq` and `:qa` remember the place of every file, as the quit of one file does. A tick that makes an App draw (the seconds of its running filter, PROP-5) draws the screen again; one that changes nothing draws nothing.
  - **Decided** (P1): `:e name` opens another file and never replaces this one, so it is not refused when this file is modified (`:e! name` is the same); `:e` and `:e!` without a name reload this file by si's rules. A directory named by `:e` is revealed in the panel (the panel opens, focused, with it expanded and under the cursor, reading what is not there yet); outside the tree's root it says so. A file is the same file when its journal key (its canonical path) is the same, whatever its name: opening a second name of an open file shows the first, because two buffers on one key would overwrite each other's snapshots.
  - **Decided** (P1): a file whose snapshot was recovered keeps that snapshot until its own is on disk, as in si; the journal thread keeps one such snapshot for each file.
  - **Decided** (P1): the state directory of snapshots and recovery copies is si's, by si's own functions, so that si and sim recover each other's files and the rule has one home: `journal::state_dir` (`$XDG_STATE_HOME/si`, else `$HOME/.local/state/si`, a relative path ignored, none otherwise, never `/tmp`), `journal::write` and `file::save` (they make it 0700 and use it only if it is a real directory, not a symlink, owned by the user, with no access for group or others) and `journal::find` (it looks only at a private directory, and only at files owned by the user, so a snapshot of someone else's is never read). With no directory, or one that is not private, snapshots are off: none is written, none is looked for, and a save that needs a recovery copy (SAFE-2's in-place save) fails instead of writing it anywhere else; the journal thread says why once, on the status line, when the first snapshot cannot be written (`cannot write snapshots: {why}`), as in si. sim's own copies of these (`snapshot_dir`, `private`, `foreign`, a dead path for the save thread) are gone; the history is in `$XDG_STATE_HOME/sim`, next to si's directory by the same rule (MARK-2). Checked with threads on a private, an open and a linked directory, and on none; the owner test itself is si's (a test cannot make a file for another user).
- **BUF-2** [P2][S1] Tab and Shift-Tab switch to the next and the previous open file (BufferLine's keys in the author's nvim). With more than one file open, the status line shows its position, e.g. `2/5` — U
  - **Decided** (P5): the keys wrap round. They are sim's when the current App is in Normal mode with nothing pending (a count, an operator, a prefix), also while the panel has the focus; in any other state Tab goes to the App (a tab in Insert mode, a space on the command line) and Shift-Tab, which si has no key for, is dropped. REVIEW (PROP-8) is such a state, with a hunk open or not: Shift-Tab does nothing and REVIEW stays; Tab goes to the App, which ends REVIEW as any key but `y n Y N ]c [c` does, and does not switch files. In the panel the same: with the App in REVIEW, Tab and Shift-Tab do nothing. The position is added after the status text or the message, but not on the command line.
  - **Decided** (P2): the position `2/5` is never cut: the status (the App's, a message, the TREE line, the search) is cut to what the position leaves of the width, and the App is asked to lay its status out at that width (the same second render as for the command line), so that its own state words are the ones kept.
- **BUF-3** [P1][S1] `:q`, `q`, `ZQ`, `:x`, `ZZ` and `:wq` close the current file with si's rules; closing the last one exits. `:qa` exits when no file is modified and otherwise names the modified ones; `:qa!` discards them all; `:wa` saves every modified file. The exit code follows si's (`:cq` is 1) — I
  - **Decided** (P1): an App's `Quit(0)` closes that file (it has asked the journal to forget the file's snapshot already); the file after it shows, the one before if it was the last; closing the last one exits with 0. Any other code is `:cq`: sim ends with it at once, the file `:cq` was typed in is given up as in si, and every other modified file gets a last snapshot as a signal would ask for, which stays. A signal gives every file the signal, so each modified file's snapshot is asked for, and sim exits with 128 + the signal.
  - **Decided** (P1): `:qa`, `:qall`, `:qa!`, `:wa` and `:wall` are taken when Enter submits them, before the App sees the line. `:qa` with modified files says `no write since last change in a.rs, b.rs (:qa! to discard)` and does not quit; `:qa!` and a clean `:qa` ask the journal to forget every file's snapshot and exit with 0. `:wa` saves each modified file as Ctrl-s does (so each is checked against its own disk, SAFE-5); each file tells its result in its own status line, and `no modified files` when there is none. `:wqa` and `:xa` are not built.
  - **Decided** (P1): SAFE-7 holds for each file. `:qa` is refused while any file has a hunk open (a conflict with the disk now, a filter's proposal at M4), whether or not it is modified, and names those files: `unresolved proposals in a.rs (]c to review, :qa! discards)`, which it says instead of `no write since last change`, as si's `:q` does; once they are decided it tells the modified ones. `:qa!` quits with hunks open and writes nothing. `:wa` leaves out the modified files that have a conflict with the disk (their hunks with `disk` set) and saves the others as before; it names the left-out ones on the status line, `not saved: conflicts with the disk in a.rs (]c, :w! keeps yours)`, which replaces the current file's own message. `:w!` in a file keeps mine as si says. The other commands (`:q`, `:x`, `:wq`, `q`, `ZZ`) are the App's and refuse in the file they are typed in, closing nothing (checked).

## Finding

- **FIND-1** [P2][S2] `/` in the panel searches every file under the root, not only the expanded ones, as you type (search-directed navigation): the cursor goes to the best match, expanding the directories on its way; every match and the directories leading to it are bold, everything else is dimmed; nothing is hidden or reordered. `n` / `N` go to the next / previous match, Enter opens, Esc ends the search and restores the expansion — U
  - **Decided** (P2): a path matches when the query's chars occur in it in order; smartcase applies to the whole query (one uppercase letter makes it exact); an empty query matches nothing. The match is taken in the file name when the query occurs there, else in the whole path, and is the tightest one that ends first (the earliest end, then the latest chars before it). This is a heuristic, not the best alignment: that costs a table per path, too slow for FIND-3. A search returns every hit in the order of the list with the char positions of its match (chars, not bytes) and the set of directories above the hits (`/`-separated, relative).
  - **Decided** (P2): `/` in the panel and Ctrl-p anywhere (FIND-4) start a search; the cursor row and the open directories are remembered for Esc. While the query is typed: a char is added, Backspace takes one off (and ends the search when none is left), Enter opens the best match at once, Down and Up stop the typing and step to the next / previous match, Esc ends the search; every other key does nothing. Enter ends the search with the expansion put back to what it was before it, and then only the directories of the opened file opened (the reveal `:e` uses), so that the tree shows where the file is and nothing the cursor passed on its way (the best match of `i` or `io` is not the file `io/filter` was meant to find; Esc's restore and Enter's leave the same debris-free tree, P2); `n` and `N` are for the matches that stay lit after Down or Up (when typing they are chars of the query, and Enter opens at once, since quick open is P2's shortest way). In that state the panel's own keys work as usual, `/` starts a new query, Enter on a file opens it and ends the search the same way, Esc ends it (the expansion and the cursor are what they were) and a second Esc gives the focus back.
  - **Decided** (P2): the cursor follows the best match by revealing its directories as their listings arrive (the same step-by-step expansion `:e dir` uses), so a match in a directory not read yet is shown a moment later; Enter opens the match by its path, not the row under the cursor, so it does not wait for that. A key of the panel's own cancels a reveal still waiting. `n` and `N` walk the matches in the order the rows are on screen (directories first, then names, the order of TREE-3: `tree::cmp_paths`) and wrap round; the next match is found by a pass over the hits, so the work of one `n` is that of one key of the search.
  - **Decided** (P2): bold is the whole row of a match, and of a directory with a match somewhere below it, even when it is closed; the rest is dimmed (si's secondary style); an empty query lights nothing, a query with no match dims everything and the status line says `/{query}  no match`. The status line is `/{query}  {n} match(es)` while a search runs, with the terminal's cursor at the end of the query while it is typed. A change to the list of files (FIND-3) while searching runs the search again.
  - **Decided** (P2): in the search line the query is cut from the left when it is longer than the screen and the count of matches (`  3 matches`, `  no match`) stays; the terminal's cursor is at the end of the query shown.
- **FIND-2** [P2][S2] Matching is fuzzy on the path relative to the root (its characters in order, smartcase), ranked by the quality of the match and then by MARK-2's likelihood — U
  - **Decided** (P2): the score uses fzf's scale, untuned: 16 a char, -3 to start a gap and -1 more a char in it, 4 for chars that follow each other (a run keeps the bonus of its first char), 8 for a char after a word edge (` _-.`), 9 after `/` or at the start, 7 for a camelCase hump; plus 12 when the match lies in the file name. The better hit has the higher score, then the higher likelihood, then the shorter path, then the smaller, so the order never depends on the order of the list. The path's length is a tiebreak after the likelihood and no part of the score (fzf's `--tiebreak=length`): as part of the score, a shorter path (`tests/review.rs`) beat a longer one (`src/core/review.rs`) by a point, the scores never tied, and the likelihood of the file you had just opened was never consulted, in the case it matters most (`mod.rs`, `index.ts`, `README.md`, `review.rs` in src and in tests). `best` finds the first: the cursor goes there.
  - **Decided** (P2): the likelihood of a path comes from MARK-2's history with the absolute path (`{root}/{path}`) and the current time, and counts only among the hits that have the top score. The history is at most 1,000 paths, so the work is theirs (each found in the sorted list by binary search), never one per hit of the top score, which can be most of 100,000 paths. Opening a file records it, so the file just opened wins ties the next time.
- **FIND-3** [P4][S2] In a git repository the files come from `git ls-files --cached --others --exclude-standard -z` (so ignored trees such as `target/` don't flood the search); elsewhere from walking the directory. Both run in the background. One key of the search takes at most 16 ms on 100,000 paths — B
  - **Decided** (P4): measured on a release build (AMD Ryzen 9 9950X) over 100,000 synthetic sorted paths of 40 chars: the worst key of `s sr srv c cl client clientrs u ut utl q zzzz` takes 6.7 ms with ten files to a directory and 9.8 ms with a directory of its own for every file (the worst case for collecting directories), including the pass, the directories and `best` with a history of 200 files. A query that matches nothing takes 3.6 ms. `cargo test --release -p sim --test find -- --ignored bench --nocapture` prints them. ASCII paths are scanned as bytes.
  - **Decided** (P1): `io::git_files` returns git's NUL-separated bytes, relative to the directory asked; git runs with `--no-optional-locks` (a background status must not take `index.lock` from the user's own git) and `LC_ALL=C`, so that "not a git repository" is told from other failures in any language: the error is `not a git repository: {dir}`, any other `git {command}: {message}`, and a directory that cannot be entered `cannot run git in {dir}: {why}`.
  - **Decided** (P4): the list is asked for at the start and whenever the panel opens (Ctrl-n, Ctrl-p), and runs in a thread of its own (`io::worker`) that never runs twice at once: requests made while it runs are one more run after it, however many there were. A walk (no repository, git cannot be run, or git is skipped for the repository's config, MARK-1) skips directories named `.git`, never follows a link (a link is a file), and stops after 200,000 files, so that a walk of `/` or of a home directory does not eat memory; git's list has no limit. The list is sorted (bytes) and has no duplicates, which the panel's search needs to look a row up by binary search. A file git lists as tracked but that is gone from the disk is in the list; opening it makes a new file, as `:e` of a name that does not exist does.
  - **Decided** (P4): measured on a release build (AMD Ryzen 9 9950X) over 100,000 files in 1,000 directories: `git ls-files` through `io::files` takes 30 ms, `git status` 154 ms (both in their threads). The worst key of a search through `Sim::update` itself, with the frame, is 6.6 ms (7.1 ms measured again on 2026-10-16 with the length no longer in the score, FIND-2, on a busy machine: load average about 10; the worst key of `cargo test --release -p sim --test find` 10.5 ms) (`cargo test --release -p sim --test find_panel -- --ignored bench --nocapture`).

- **FIND-4** [P5][S2] Ctrl-p from anywhere opens the panel and starts `/` (Telescope's find_files key in the author's nvim), so the hands that reach for quick-open land in the tree's search — U
  - **Decided** (P5): Ctrl-p is sim's in every mode (Insert and the command line too) and never reaches the App, like Ctrl-n. It opens the panel if it is closed (reading what may have changed, as Ctrl-n does), gives it the focus, ends a search that was running and starts a new one. The panel stays open after Enter opens a file; Ctrl-n closes it.
## Marks

- **MARK-1** [P2,P3][S2] Files that git reports as modified, added or untracked, and files that changed on disk while sim runs, get the change color on their name, and every directory above them gets `~`, so a change can be found from the root. The status comes from `git status --porcelain=v1 -z` in the background, run again when files change — U
  - **Decided** (P2): status runs with `--untracked-files=all`, so that every untracked file has a name to color and not only its directory. A renamed file marks the new name, and the old name's directories (something left them); a copy marks only the new name. A deleted file marks the directories it was in. All of them are paths relative to the top of the repository, so `Marks::new` takes the root's `prefix` below the top (`git rev-parse --show-prefix`, which `io::git_prefix` runs) and leaves out what is outside the root. Entries that do not parse are skipped.
  - **Decided** (P1): git runs without a shell, with `-c core.fsmonitor=false` and `--no-optional-locks` (a second line of defense after the next item, which already keeps a repository that defines a monitor from being asked); `git status` also runs with `--ignore-submodules=all`, because git would run a child git in each submodule, under the submodule's own config, which the guard did not read (and `git ls-files` does not recurse into submodules): checked with a submodule whose own filter and monitor leave a witness file, which plain git makes and sim does not.
  - **Decided** (P1): sim never runs git where the repository's own config could make it run a command. Before `git status`, `git ls-files` or `git rev-parse` it asks git for the config of the repository around the directory (`io::git`, next item), and git is not run (`io::git` answers `git skipped: this repository's config could run commands`) if the repository defines anything that can hold a command (the class of the next item, which takes in a `filter` driver, `core.fsmonitor`, `core.hooksPath`, `core.alternateRefsCommand`, and an `include` or `includeIf` that can bring any of them in), or if git cannot read the config. The user's own configuration (system, global, the command line) is trusted, and git's `safe.directory` check still limits repositories owned by someone else. A repository without a config file is run. The status line says it once per session, on the first answer, and the panel shows no marks (files that change while sim runs still get theirs); the files come from the directory walk of FIND-3 (so ignored trees are in the search). Checked with temporary repositories (no global config, as check.sh runs them) for every kind of definition above, in the forms that git reads and a parser of sim's own may not (dotted sections, `config.worktree`, continued values, includes, case, quoting), a worktree, a separate git directory, a fake `.git` over a real repository, an unreadable config and one that does not parse; and with a filter and a monitor whose command leaves a witness file: plain git makes the witness, sim does not.
  - **Decided** (P1): the config is read by git itself, not by a parser of sim's (a second parser can disagree with git: continued values, dotted `[filter.x]` sections, `config.worktree`, includes). sim runs `git -c core.fsmonitor=false config --list --show-scope -z` in the directory (reading config never runs a command: `builtin/config.c` only parses and prints, and starts an editor for `--edit` alone) and skips git when any entry of the repository's own scopes (local, worktree, and the files they include, which have the scope of the file that includes them) has a key that can hold a command, as a class and not a list of today's uses (so a setting git adds later is in it): the section is `filter`, `include` or `includeif`, or the variable (the last dotted component) is `driver`, `textconv`, `helper`, `process`, `clean`, `smudge`, `askpass`, `editor`, `pager`, `gitproxy`, `hookspath` or `fsmonitor`, or ends with `command`, `cmd`, `program` or `hook`; the ordinary keys of a repository (`core.repositoryformatversion`, `remote.*.url`, `branch.*.remote`, `user.*`, `submodule.*.url`, `lfs.url`) are not. Git lists section and variable names in lower case and keeps the case of a subsection, so the keys are compared as they come. The user's system and global scopes, and the command line's, are trusted; any other scope and a listing that does not parse are not. An error from `git config` (an unreadable file, one that does not parse) is a skip with the same message; "not a git repository" is told as for any other git command, and the directory is walked without a message. Outside a repository, and where git refuses the repository for its owner, `git config` lists the user's own config and succeeds; the command that follows then fails by itself before it runs anything.
  - **Decided** (P2): git is asked at the start, whenever the panel opens, after a file is saved and when a file changes on disk, in a thread that never runs twice at once (`io::worker`, as for FIND-3). The paths of files that changed on disk while sim runs are the ones sim saw itself: a change reported by the watcher of an open file, and a save of one (a save is a change too, and without git it is the only news). They are relative to the root, so a file outside the tree is not marked. In a directory that is not a repository the status is not asked again until the panel opens (a repository may have been made); another failure of git is told on the status line.
  - **Decided** (P3): in the panel the change color (si's Change style) is on the name of a changed file only, `~` follows the name of a directory with a change below it (` ~`, after the `/`), and a closed directory shows it too. The change style wins over everything else on a name: over the dimming of a search, over a syntax color.
- **MARK-2** [P2][S2] sim remembers which files you open (in its state directory) and ranks them by recency and frequency together, in the spirit of AccessRank. The five likeliest files are marked with `•` where they are in the tree — U
  - **Decided** (P2): likelihood(path) is the sum, over the times it was opened, of (age in seconds, at least 60)^-1/2. That is ACT-R's base-level activation (Anderson & Schooler 1991), a power law that fits real access streams: one open a minute ago beats many from last week, yet opens add up, so recency and frequency count together as in AccessRank. It is not AccessRank itself (which also learns from the sequence of accesses). The history is bounded at 16 opens a path and 1,000 paths (the least likely go); a file opened daily for years must not outweigh today's work, and 1,000 files is far beyond one person's working set. Keys are absolute paths; `top(root, n, now)` returns the paths below `root`, relative to it.
  - **Decided** (P1): the history file is `$XDG_STATE_HOME/sim/history`, else `$HOME/.local/state/sim/history` (a relative `XDG_STATE_HOME` is ignored, as the XDG spec says); with neither there is no history, never a fallback to `/tmp`. The directory is 0700, the file 0600, and a save is a temporary file in the same directory, synced, then renamed over the old file, then the directory is synced. One line a path: the times in hex, a tab, the path; a path with a line break is not remembered. Reading skips what does not parse and applies the bounds, so a damaged or edited file cannot do harm; an unreadable file is an empty history. Two sessions saving at once: the last save wins.
  - **Decided** (P2): an open is recorded when the user chooses a file: Enter, `l` or Right on a file in the panel, a match opened by Enter, `:e name`, and the file named on the command line; showing a file that is open again counts, Tab does not. The time is the shell's: seconds since the epoch at the start, and the ticks (one a second) after it. Each record asks the shell to save the history; the saves are jobs of the journal thread, in order, so sim waits for the last one on exit as it does for snapshots, and the first failure is told once on the status line.
  - **Decided** (P2): a directory is not a file that was opened. `:e dir` (and Enter on a link that leads to a directory, which the panel lists as a file) is noted when it is asked for, before the shell can tell, so the shell's answer that it is a directory (`SimEvent::Dir`) takes it out of the history again: left in, it filled one of the five `•` and, in the narrowed tree (MARK-3), stood in the place of the directory, so that the recent files below it vanished. A path is noted in its lexical form (`./a` and `a` are one key, as the same file is for BUF-1), so that the opens of one file add up.
  - **Decided** (P2): `•` is where a file's marker goes (the two columns left of its name that a directory spends on `▸`), so no name moves; it is shown for the five likeliest files whose directory is open, and not on a directory.
- **MARK-3** [P2][S2] `.` in the panel narrows the tree to the files that changed, the open files and the recently opened ones, with their directories (as Mylyn's task context); `.` again shows everything — U
  - **Decided** (P2): the files kept are those git (or the disk) says changed, the open files and the recent ones: a file opened as often as one opened once a day ago counts (likelihood 1/sqrt(86,400) = 0.0034; the history is bounded at 1,000 files), so that "today's work" is the horizon, not an arbitrary count. The narrowed tree is a `Tree` like the other, made from listings that hold only these files and the directories above them, all open; so its keys are the panel's (`h` closes a directory, `-` closes all). It is made again when the marks, the open files or the history change. `.` pressed again shows the whole tree with the entry under the cursor revealed (its directories are opened, reading what they need), `/` and Ctrl-p leave the narrowing, and a deleted file that git reports is in it (opening it makes a new file).

## Highlighting

- **SYN-1** [P3][S3] Syntax highlighting colors the text with the terminal's own palette, read with OSC 4 the way si reads the background with OSC 11 (VIS-4): keywords red (and bold), strings green, numbers and constants magenta, types yellow, functions cyan; comments in the secondary gray and italic; everything else primary. Blue is never used, being near the change hue (250). Each color keeps its hue but is moved in OKLCH lightness until |Lc| ≥ 75 against the background, so the theme stays and the text stays readable. Without an OSC 4 reply, SGR 31–36 stand in — U (golden)
  - Changed from "lightness and type only" at the author's request (sim is for convenience); P3 still holds, because the change is a background and its hue is kept free.
  - **Decided** (P3): scopes map to looks by the longest matching prefix in a table (`RULES` in `syn.rs`); where the scopes of a char disagree, the order of `Look` decides: comment, string, keyword, number, type, function, so a keyword inside a comment or a string stays a comment or a string. Comment: `comment`. String: `string` (but not `string.unquoted`: a bare word, YAML's plain value, bash's `$(...)`) and `constant.character`. Keyword: `keyword` (but not `keyword.operator`, except `CMD` of a Dockerfile), `storage` (not `storage.type.string`, the `f` of an f-string, and not lifetimes) and `variable.language` (this, self, super). Number and constant: `constant`. Type: `support.type`, `entity.name.type`, `.class`, `.struct`, `.enum`, `.trait` and `entity.other.inherited-class`. Function: `entity.name.function`, `support.function`, `support.macro` and `variable.function`. Markdown headings and strong are bold with no color. Operators, names and punctuation are plain. Known quirk of bat's Rust syntax: `let` and the primitive types (`u8`, `str`) share the scope `storage.type`, so both are keywords.
  - **Decided** (P3): keywords are SGR 1;31 (bold red), strings 32, numbers and constants 35, types 33, functions 36, comments italic (3) in si's secondary gray, or 2;3 (faint and italic) while there is no palette of si's (VIS-4). The change style wins: on a char that has it a look can be bold or italic but never a color, because reverse video would turn a text color into a background (P3: the change is the only chromatic background).
  - **Decided** (P3): the background is si's: `term::enter` asks for it (OSC 11) right after the screen is switched, si's `Reply` puts the answer together out of the keys and makes `Event::Bg`, the first frame waits for it at most 3 ms, and a late answer redraws everything, all as in si's main. sim gives `Event::Bg` to every App (so si's APCA palette, VIS-4, paints Primary, Secondary, Change and Deleted in every Frame, by `term::sgr`) and to the syntax colors; a file opened later is told it as soon as it is open. sim's own OSC 11 handling is gone. When COLORTERM is `truecolor` or `24bit`, sim also asks, after the first frame (never before it), for ANSI red, green, yellow, magenta and cyan (OSC 4; blue is never asked for). Their replies come in as keys too (crossterm reads `ESC ]` as Alt+`]`, the payload as plain keys and `ESC \` or BEL as Alt+`\` or Ctrl-g); `color::Input` is in front of si's `Reply`: while replies are still to come (five were asked for, and they are counted as they arrive, however late: over a slow link they take seconds, and a reply that is not put together here is typed into the text, as keys, `cc` and `r` among them) an Alt+`]` is held until the next key says which reply it begins (`4` is sim's, anything else goes to si's `Reply` with the held key, in order; si's `Reply` holds an Alt+`]` for OSC 11 as long, so a typed Esc and `]` wait no longer than before), and an OSC 4 reply is put together here and never reaches the App; a key that turns out not to belong to a reply goes on as a key. Each color is then moved in OKLCH lightness, away from the background (lighter on a dark one: the side with more contrast to give), in steps of 0.01 until |Lc| ≥ 75 (si's `apca`; APCA-W3 0.0.98G-4g), keeping its hue and chroma (chroma shrinks only to fit sRGB, by si's `oklch`). Without COLORTERM, or for a color without a reply, or without a background reply, SGR 31–36 stand in. A late reply redraws the screen. `color.rs` is what si's `core::color` does not provide: the other way round of `oklch`, the contrast loop, the selection's gray and the assembling of OSC 4.
  - **Decided** (P1): no answer of the terminal may be typed into the shell (VIS-4): sim's quit does what si's does. When the background or an ANSI color may still be on its way (`Sim::asking`), the quit wakes the input thread (SIGWINCH), which asks the terminal for its attributes (`CSI c`, answered after everything asked before) and tells the quit, which waits for that for at most 100 ms before it gives the terminal back. Checked with si's `scripts/pty_bench.py leak` against sim's binary: a terminal that answers 30 ms late, in order, and `:q` at the first frame leaves no byte for the shell; a terminal that answers everything, or all but OSC 11, costs a quit under 80 ms, one that answers nothing about 100 ms.
  - **Decided** (P2): si's `Row` has four styles and no color of syntax, so sim composes its own `Screen` (si's `Frame`, which carries si's palette, the looks of each row, the syntax colors) and draws it with `paint::Painter`, si's `Term::draw` with looks (the four styles are si's `term::sgr`; the looks go on top). The looks of an editor row come from the frame: the line is read from its gutter, its chars from the buffer, and the columns of each char by the rules of view.rs (a tab to the next multiple of 4, `^X`, `<U+XXXX>`, the width of the char); a wrapped line goes on in the rows below. The columns of a char are si's own `view::width` (VIS-7's emoji sequences included) in the looks of a row, in the painter (so that a span starts where si's `Term` starts it) and in the panel's names (`layout::fit`); what is repeated is only which chars si writes as `^X` or `<U+XXXX>` (`layout::hostile`, with U+061C since SAFE-8's decision), and a golden with tabs, wide and control chars and a test with emoji sequences and the bidirectional controls keep the two together.
  - **Decided** (P3): in REVIEW (PROP-8) a file has no syntax colors: its rows weave mine and theirs into one text, so a row's text is no longer the buffer's line the colors were made for. The change is what is looked at there; the colors come back when REVIEW ends.
- **SYN-2** [P2][S3] It is on by default; `zh` turns it off and on for the session — U
  - **Decided** (P2): `zh` is taken when the `z` was typed in Normal mode with nothing pending and the next key is `h`; the App still gets both keys (its parser drops `zh`), so `zz` and a count in between are the App's. The status line says `syntax colors off` or `on` until the next key. It holds for every file until sim ends.
- **SYN-3** [P4][S3] Highlighting never delays a key: per-line parse states are cached, and a jump that needs parsing from far above is parsed in the background (those lines show plain until it arrives). Files over 10 MB are not highlighted — B
  - **Decided** (P4): `Syn` keeps the parse state at the start of every 16th line (`EVERY`); an edit at line E keeps the states at or above E, and the next call parses again from the last of them. A line takes about 40 us to parse (release, fancy-regex), so the edited line is back after at most 15 lines, 0.6 ms measured (a step of 32 measured 1.2 ms, over SPEED-1's 1 ms; a step of 8 costs five times the memory for 0.2 ms). The states of 70,000 lines held 1.1 MB resident. A cold first window of 50 Rust lines takes 17 ms (the syntax's contexts are decoded and its regexes compiled the first time it is used) and loading the syntax set 0.6 ms (bat's set, SYN-4): both are in the highlighter's thread, never before the first frame. A jump 10,000 lines below the cached states takes 0.4 s. Spans are not cached in `Syn`, only states; the spans of the window on screen are kept by `Sim` (below). `cargo test --release -p sim --test syn_bench -- --ignored bench --nocapture` prints these.
  - **Decided** (P4): all parsing is in the highlighter's thread (`io::highlight_thread`), which owns a `Syn` for each file, so no key waits for it, near or far. `Sim` asks for the lines on screen plus a screenful above and below (as a `Req` with a clone of the buffer's rope, which is O(1)) whenever the text changed or the window is not covered, once for each window and version, and shows the answer (`Hl`) when it arrives. Until then, and after an edit, the spans of the last answer are used (an edit leaves the colors of the other lines as they were for a few milliseconds); when lines were inserted or removed at the cursor, the spans of the lines below it are shifted by the difference, so Enter or `dd` does not make the screen flash plain. Of the requests waiting, the newest for each file is answered. The thread finds where the text changed by comparing the new rope with the one it parsed last (the first chunk that differs), so undo, paste, `:s` and a reload are all handled without the App saying where, and tells `Syn::edit` that line; ropes cut into chunks in another way count as different where their chunks first do, which only costs a longer parse.
  - **Decided** (P4): files over 10 MB (`sim::sim::MAX_HL`) are never asked for. Measured on a release build (AMD Ryzen 9 9950X), a window of 70 lines of a 100,000-line Rust file: the first one (loading the syntaxes) 17 ms, an edit at line 50,000 with its window 3.7 ms mean and 3.9 ms worst (4 MB of text compared included), a window where the states are cached 3.3 ms, a first window 50,000 lines down 2.6 s (plain until then). A key on the main thread, with the panel open, colored text and a history of 1,000 files, takes at p99 90 µs (80x24) and 410 µs (240x60) (SPEED-1). `cargo test --release -p sim --test syn_bench -- --ignored bench --nocapture` prints them.
  - **Decided** (P4): the main thread finds the span of a char by binary search (`layout::colors`; the spans of a line are in order and apart): scanning them made each plain char of the screen cost all the line's spans, so a long line with many (a minified file, 18,000 spans in 100,000 chars) took 7 ms a key instead of the 0.1 ms the rest of the frame takes, measured with a release build.
  - **Decided** (P4): a line of more than 10,000 bytes (`syn::MAX_LINE`) is plain and is not parsed, and the parse state stays as it was before it, so that the lines after it do not start from a guess. The time one line takes is bounded: with the pure-Rust regex backend some syntaxes take time that grows with the square of the line (measured on a release build, a shell heredoc whose word is 100,000 chars: 5.8 s; `A<` 30,000 times in TypeScript: 0.4 s; the rest of 45 languages and shapes of 100,000 chars: 0.2 s or less), and the highlighter is one thread for every file, so one such line made every other file wait and kept a core busy at every edit. Code with lines this long is minified or generated; it is the Spec's P4 (speed) that decides, and no higher principle asks for colors there.
  - **Decided** (P4): `ropey` is a dependency of sim for this, at si's version and features (si has it, so the build gains no code): the thread must be given the text without copying it.
- **SYN-4** [P2][S3] The language comes from the file name and extension, then from the first line (`#!`); the languages are those of bat's syntax set — U
  - **Decided** (P2): the syntax is looked up by the whole file name (`Makefile`, `.bashrc`), then by the extension, then by the first line (`#!`, `<?xml`); case is ignored. Plain text counts as no syntax. `Syn::new` runs off the first frame, since it loads the set.
  - **Decided** (P2): changed from "syntect's default set" at the author's request: syntect's default set has no TOML, TypeScript, TSX, Dockerfile, Kotlin, Zig, Svelte or Nix, which the author uses every day, and a highlighter that shows them plain is a highlighter that does not work for them. The `two-face` crate ships bat's syntaxes (213, including all of syntect's) as a compressed dump for syntect; with `default-features = false` and `syntect-fancy` it uses the pure-Rust regex backend and no onig (checked with `cargo tree -i onig`), and syntect's own `default-syntaxes` is off so that the binary holds one set only. Measured on a release build: the binary is 4.17 MB with bat's set and 3.57 MB with syntect's (0.6 MB for the extra languages; without syntect at all sim is 1.2 MB); loading the set takes 0.6 ms (0.3 ms before) and the first window of Rust 17 ms, in the highlighter's thread. Its scopes are what `RULES` (SYN-1) was written for; goldens for Rust, Python, shell, Markdown, TOML, TypeScript and a Dockerfile keep them. Kotlin, Zig, Svelte and Nix have a syntax; the table says nothing special about them.

- **SYN-5** [P2][S3] The Visual selection has a neutral gray background (lightness only, |Lc| ≥ 15 against the background, text on it |Lc| ≥ 75), as in common editors; si's underline stays for terminals without truecolor — U
  - **Decided** (P2): the gray is the background's own lightness moved (away from it, as for SYN-1) with no chroma until |Lc| ≥ 15, and its text is a neutral gray moved until |Lc| ≥ 75 against it; both are computed with the colors of SYN-1 (so they need COLORTERM and a background reply; otherwise the selection is si's underline). ## Pointer

- **PTR-1** [P2][S4] The mouse: a click in the panel moves there (a click on a file opens it, on a directory toggles it); a click in the text moves the cursor; the wheel scrolls what is under the pointer; dragging in the text selects as Visual mode does — I, E
  - **Decided** (P2): sim reports the mouse in SGR coding (1006) with button events (1000) and drags (1002), asked for after si's `enter` and given back before si's `leave` by every way out: a quit, SIGTERM and SIGHUP (they end in the quit), and the panic hook (`paint::leave`, which writes `MOUSE_OFF`, the reverse of `MOUSE_ON`, and then si's `term::leave`); the E2E cases ask tmux which mouse modes the pane has on, while running and after each way out. Only the left button acts; the other buttons, a pointer that only moves, and the horizontal wheel are ignored. A pointer is in the panel (its columns, the rows of the body), in the text (after the blank column), in neither (the blank column, the status line), or on the status line: the last two take every event and do nothing with it.
  - **Decided** (P2): a click on a row of the panel puts the panel's cursor there and gives it the focus, and does what Enter does there (TREE-4): a file is opened (and the focus goes to the text, as it does for Enter), a directory that is closed is expanded and one that is open is collapsed; a click below the last row does nothing. It cancels a reveal that waits for a listing, as a key of the panel's own does, and a search that is typed stops being typed (the matches stay lit; a click on a file opens it and ends the search, as Enter does).
  - **Decided** (P2): a click in the text gives the text the focus and puts the cursor on the char under the pointer, as a key that moved it would: through the App's own `clamp` (a Normal-mode cursor rests on a char, not after the last one; Insert mode may be after it), with the wanted column starting again and the mark of the line it enters seen (PROP-9). The char is found through the frame the user sees (`layout::hit`, the walk of `layout::colors`): the line of a row is read from its gutter, a wrapped line goes on in the rows below, a tab, a wide char and the tokens of SAFE-8 (`^X`, `<U+XXXX>`) take the columns si gives them (`view::width`), so a point on any column of a char is that char; a point in the gutter is the start of its row, past the end of a row that goes on the last char of the row, past the end of a line the end of the line, and below the text the last line. In REVIEW the rows weave mine and theirs, so there only the line of the row is told (its start). While a command or a search is typed on the command line, a click or the wheel in the text does nothing to it.
  - **Decided** (P2): a drag begins with a press in the text and goes on with the pointer. The first move to another char starts Visual mode where the press put the cursor, by the key `v` (so its looks and keys are Visual's), and from then on the pointer's char is the cursor; going back to the press leaves one char selected; a pointer outside the text is at its edge (above the first row the first row, below the last the last, left of the text the start of its row); releasing keeps the selection, and the next click ends it (as Esc would). Insert mode and a half-typed command select nothing (a `v` would be text), and a selection ended by a key meanwhile is not taken up again. Double and triple clicks, scrolling by dragging past the edge, and the right and middle buttons are not built (NOTES).
  - **Decided** (P2): the wheel over the text scrolls it three lines a notch (a wrapped line counts as one: the App's view starts at a line), and the cursor keeps the context VIS-12 gives it: sim sets the App's top and has `render` lay the screen out; while `render` pushes the view back to keep the cursor in its context, the cursor moves towards the view by the lines it was pushed (keeping its column), so the cursor moves only when it has to. A scroll that moves nothing (the text's end, or a text that fits) leaves the cursor where it was; the mark of the line the cursor ends on is seen. The wheel over the panel scrolls its rows three a notch and keeps the panel's cursor on the screen; it gives no focus. In REVIEW the wheel goes on looking and REVIEW stays (nothing is decided); on the command line the wheel does nothing.
  - **Decided** (P4): an event of the mouse is timed as a key is (SPEED-1's bench, kind `mouse`). A wheel notch and the first move of a drag render the App's frame twice (the cursor goes where the first render showed it must; `v` renders), so the bound for the mouse is twice a key's.
- **PTR-2** [P1][S4] The mouse never edits by itself: a click changes the cursor, the focus, the scroll and the selection only; clicks during REVIEW only move the focus and the cursor and leave REVIEW like any key that is not a decision; a click in the status line does nothing — I, E
  - **Decided** (P1): the mouse does not complete what a key began, and does not decide for the user: a click forgets a count, an operator or a prefix that waits for the rest of its command (Esc to the App: `d`, a click, `w` deletes nothing), ends a Visual selection, and leaves REVIEW (nothing is accepted or rejected, the hunks stay); the wheel forgets a half-typed command too, but leaves REVIEW and a Visual selection alone. Nothing the mouse does is an edit, a save, a snapshot, a filter or a copy: checked by running thousands of events of every kind at every place, in every mode, against two files, on screens from 80x24 down to 3 columns and 2 rows, and looking at the text, the modified flag and the effects asked for (a click on the panel may open a file, which is no edit). The smallest screens found that a screen narrower than its gutter, whose line numbers are cut, made `Sim::colors` ask the highlighter for a window that ends before it starts: fixed.
