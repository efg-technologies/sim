# SPEC — si

Format: `- **ID** [principle][milestone] requirement — verification`

Kinds of verification: U = unit/property test, I = integration test (feed an event sequence to App), E = terminal E2E (tmux), B = benchmark.
Test names start with the ID in lowercase (SAFE-1 → `safe_1_...`). scripts/trace.sh checks the mapping.

Sub-items that start with **Decided** record what was settled while implementing, with the principle that settled it.
They bind the implementation the same way as the line above them.

## Startup and exit

- **CLI-1** [P5][M1] `si [+cmd] [file]`. `+N` goes to line N, `+/re` searches, and any other `+cmd` runs as an ex command. It runs after the first render — I
  - **Decided** (P5): `--` ends the options, so a file named `+x` can be opened. Any other argument that starts with `-`, or a second file, prints usage and exits with 2. Without a file, si opens an unnamed buffer, and `:w {file}` gives it that name.
- **CLI-2** [P3][M1] `file:line[:col]` is accepted. But if a file whose name is exactly that string exists, that file is opened — U
- **CLI-3** [P5][M2] The exit code is 0 for `:q` `:wq` `:x`, and 1 for `:cq` (used to abort git commit) — I
  - **Decided** (P5): `:q!`, `ZZ`, `ZQ` and `q` exit with 0 as well, so `:cq` is the only way to fail on purpose. `git commit` with `GIT_EDITOR=si` is checked end to end: `ZZ` commits and `:cq` aborts.
- **CLI-4** [P1][M1] Every way out, including panic, SIGTERM and SIGHUP, restores the terminal state — E
  - **Decided** (P1): SIGTERM and SIGHUP reach App as an event. Unsaved changes are snapshotted (SAFE-6) before exiting with 128 + the signal number.
  - **Decided** (P1): a failed write to the terminal counts as a hangup: it reaches App as SIGHUP, so the unsaved text is snapshotted and si exits with 129, instead of leaving at once with 1.

- **CLI-5** [P2][M4] `si` without a file shows an intro until the first key, like vim's: what si is, and the keys to type, save, quit and review. The view draws it; it never becomes text, and it doesn't show when recovered text fills the buffer — U (golden)
  - **Decided** (P2): the intro is plain text in the two achromatic levels: `si {version}` (the Cargo version), the one line of CONCEPT, and the keys to type, save, quit and review (`i / Esc`, `Ctrl-s`, `ZZ`, `q`, `ZQ`, `]c then y / n`), centered below the first row (which keeps the empty line 1 and the cursor). It is at most 12 rows; the lines that don't fit a short screen are dropped from the bottom, and a narrow one cuts them. It goes with the first key (or when text is in the buffer), and it is never part of the buffer.

- **CLI-6** [P2][M4] Reopening a file puts the cursor where it was when the file was last closed (remembered per file in the state directory, for the last 1,000 files), so reading continues where it stopped. Not with `+cmd` or `file:line`, and not for git's message files (`COMMIT_EDITMSG`, `MERGE_MSG`, `TAG_EDITMSG`, `git-rebase-todo`), which start at the top — I
  - From the author's nvim (a `BufReadPost` restore, as in vim's own defaults.vim): continuity of context.
  - **Decided** (P2): the place is the cursor's line and column (0-based). It is remembered by whatever closes the file: `:q` `:q!` `:wq` `:x` `:cq` `q` `ZZ` `ZQ`, a signal, and an `:e` (a reload too, which then puts the cursor back), and not by a quit that is refused. A buffer without a file remembers nothing.
  - **Decided** (P2): it comes back as an event after the file has loaded, and applies only to the file that is open, while the cursor has not moved, in Normal mode: the user who was quicker keeps their place. It is clamped to the text, centered (VIS-12), and applied to a read-only buffer too. The names of git's message files are matched as a whole file name (`.git/COMMIT_EDITMSG`, but not `COMMIT_EDITMSG.bak`).
  - **Decided** (P2): the key of a file is its canonical path (SAFE-6), the store is `positions` in the private state directory (SAFE-6), one `line<TAB>col<TAB>key` per line, least recently used first. The journal thread reads it again for each change, so sessions on different files keep one another's entries, and writes it atomically (a rename) but without waiting for the disk to sync it, since a place is not worth the wait at exit (PERF-1: with a sync `si +q` took 7 ms); what does not read as an entry is skipped, and a path with a line break in it loses its entry. The same thread answers the lookup for an `:e` (as an `Event::Place` after the file's `Opened`), so it comes after the place of the file that `:e` left; the first lookup is made at startup, before the first frame. Without a state directory nothing is kept between sessions.
## Safety

- **SAFE-1** [P1][M1] Saving creates a temporary file in the same directory with 0600 and O_EXCL → writes it → fsync → rename → fsync of the directory, in this order. Whichever step fails, either the old or the new version remains intact — U (fault injection at each step)
  - **Decided** (P1): before the rename, the temporary file gets the original's mode and group. If the group cannot be set, the in-place path of SAFE-2 is used instead.
  - **Decided** (P1): a symlink is saved through to its target, and the link itself stays.
  - **Decided** (P1, P5): a file that does not exist yet gets the mode any new file would get, so its temporary file is created with 0666 reduced by the umask instead of 0600. This exposes nothing the final file doesn't.
  - **Decided** (P3): saving runs on a background thread, and editing continues meanwhile. `:wq` and `:x` quit only after the save has succeeded.
  - **Decided** (P1): once the rename has happened the save counts as done, even if syncing the directory then fails (some systems refuse it); the status line says so as a warning.
  - **Decided** (P1): a dangling symlink is followed to its missing target, which is created; the link stays. A file without write permission is not saved over: `read-only file (:w! to write anyway)`; `:w!` writes it and keeps its mode.
  - **Decided** (P1): si writes through a symlink, dangling or not, only if the user owns the link; a link owned by someone else (a planted link in a shared directory such as /tmp) is refused with `not saved: x is a symlink owned by someone else`, like Linux's `fs.protected_symlinks`.
- **SAFE-2** [P1][M1] If the file is owned by someone else, has two or more hard links, or its directory is not writable, save in place. Before that, write a recovery copy and fsync it; delete it once the save has succeeded — U
  - **Decided** (P1): the recovery copy goes to `$XDG_STATE_HOME/si/` (0700), because the file's own directory may not be writable. If the in-place write fails, the status line names the recovery copy.
- **SAFE-3** [P1][M1] Opening and saving without editing gives byte-identical output (line endings, whether there is a final newline, BOM, permissions) — U (property test)
  - **Decided** (P1): if every line break is CRLF, the buffer holds LF and saving writes CRLF. Any other mix is kept exactly as it is (`\r` shows as `^M`, SAFE-8).
  - **Decided** (P1, P2): an empty or new file gets a final newline once it has text, since a text file ends with one (git and POSIX tools expect it). An existing file keeps whatever it had.
  - **Decided** (P1, P5): deleting all the text of a file and saving writes an empty file (0 bytes), as vim does; undo brings back the final-newline state with the text.
  - **Decided** (P1): text that goes and comes back inside one change (`ccxyz`) is not an emptied file: with text again the file ends as it did, so one that had no final newline has none. A file that was saved empty stays an empty file until it has text, and then ends as the file it was.
- **SAFE-4** [P1][M1] A file that is not valid UTF-8, or has a NUL in its first 8 KB, opens read-only and shows why — U
  - **Decided** (P1): invalid bytes are shown as U+FFFD. Edits and every kind of write are refused, because the text on screen is not the file. A file that cannot be read (no permission, a directory) opens the same way with an empty buffer.
  - **Decided** (P2): a directory says `<path> is a directory` (finding files is sim's job).
  - **Decided** (P2): the status line says `read-only: {path} is a directory`, or `read-only: cannot read: {why}`.
- **SAFE-5** [P1][M3] Right before saving, the hash of the content on disk is compared with the hash at load (the base). If they differ, nothing is overwritten and the disk content goes to the merge of PROP-2 — I
  - **Decided** (P1): the check runs on the save thread right before the rename (compare-and-swap). After the merge, nothing is saved automatically; the status line says the file was not saved, and `:w` saves.
  - **Decided** (P1): the message is `not saved: the file changed on disk; merged its changes (:w to save)`, or with conflicts `… merged its changes · 2 conflicts to review`. The disk content goes through exactly the merge of a watched change (PROP-2), so the two ways in give the same buffer. A `:wq`, `:x` or `ZZ` that meets a conflict does not quit; the next one is checked against what was merged. If the file is gone, nothing is merged: the status line says `not saved: the file was deleted on disk (:w to create it again)`, and the next `:w` creates it (PROP-1). A conflict on `:w {other}` is not a merge (the content is another file's): `not saved: {other} exists (:w! to overwrite)`.
  - **Decided** (P1): right before the rename (or the truncate of an in-place save) the file's stamp (device, inode, size, mtime, ctime) is checked again, and its hash only if the stamp moved. A write in the same microsecond, or a same-size rewrite within one timestamp tick of a coarse file system, can still slip through.
- **SAFE-6** [P1][M2] Unsaved changes are snapshotted at most once per second into `$XDG_STATE_HOME/si/` (0700). Opening the same file after an abnormal exit offers to restore them. At most one second of work is lost — I
  - **Decided** (P1): a snapshot holds the path, the base text and the buffer text, in a file (0600) whose name includes the process id, so two sessions on one file don't overwrite each other's snapshots. A background thread writes it (P3). It is deleted after a successful save and on quitting with `:q`, `:q!` or `:cq`; it stays after a crash or a signal. A snapshot whose process is still running is left alone.
  - **Decided** (P5): if the disk still matches the snapshot's base, restoring applies the snapshot text as one undo step, and the status line says how old they are, e.g. `recovered unsaved changes from 3 minutes ago · u to undo` (an age needs no time zone, which si cannot read without libc). If the disk has changed since, the snapshot goes through the merge of PROP-2 as `mine` (base: the snapshot's base, theirs: the disk), as one undo step, and the status line says `recovered changes from 3 minutes ago, merged with disk · u to undo`; what conflicts becomes hunks (PROP-2) and the snapshot's text stays in the buffer.
  - **Decided** (P1): the shell sends a tick at least every second, from a timer thread, so continuous typing is snapshotted too. On a tick, if the buffer is modified, its version has changed since the last snapshot and 1000 ms of tick time have passed since the last one, the App asks for a snapshot (`Effect::Snapshot`, holding the path and ropes, which are O(1) clones; the journal thread turns them into bytes). Tick times are 1000 ms apart by construction, so at most one second of work is lost. The core never reads a clock; the journal thread stamps the snapshot's time, and the shell passes the age of a recovered one in ms.
  - **Decided** (P1): the App asks the journal to forget (`Effect::Unsnapshot`) whenever the buffer becomes clean (saved, or undone to the saved text, or `:e!`) and before every `Quit` that a key or a save causes: `:q`, `:q!`, `:cq`, `ZQ`, `q`, and a successful `:wq` `:x` `ZZ`. A signal asks for a snapshot of the unsaved text, whatever the clock says, and keeps it.
  - **Decided** (P1): an unnamed buffer is protected too. Its journal key is the empty path, so `si` without a file offers the unsaved text of a crashed unnamed session. The key of a file is its canonical path, or the absolute path for a file that does not exist yet (symlinks are followed, as in SAFE-1). The App sends the path with every snapshot, because only it knows whether `:w {file}` has named the buffer or a `:e` was refused.
  - **Decided** (P3): one journal thread runs snapshots and removals in order, so a key never waits for a disk. Before si exits (`Quit`, signal, SIGHUP) the shell closes its queue and waits for that thread for at most 2 seconds, so a SIGTERM right after an edit still leaves the last snapshot.
  - **Decided** (P1): a recovered snapshot belongs to a dead process. It is deleted only once the buffer's own snapshot (which then holds the same text or newer) is on disk, or when the buffer is clean again or we quit. A snapshot that was not used (it is not applied to a read-only buffer) is never deleted by si; one that was merged is handled like an applied one.
  - **Decided** (P1): recovery runs at startup before a `+cmd`, so that command works on the recovered text (and, as with any key, clears the status message). It is not applied to a read-only buffer.
  - **Decided** (P1): a snapshot that cannot be used because the buffer is read-only is kept and left alone, and every open of that file says `kept unsaved changes from {age}, not applied: {file}`, with the snapshot's own file name.
  - **Decided** (P1): a snapshot that cannot be written is told once, on the status line: `cannot write snapshots: {why}`. The journal thread sends the first failure as an event (`Notice`) and stays quiet afterwards, since the next ticks would only say it again.
  - **Decided** (P1): the state directory must be private: it is used only if it is a real directory (not a symlink) owned by the user with no access for group or others, and snapshot files not owned by the user are ignored. Without `$XDG_STATE_HOME` and `$HOME` (or with relative paths) there is no state directory, never a shared fallback such as /tmp; snapshots and recovery copies are then off, and the status line says so once.
  - **Decided** (P1): a snapshot of a file that no longer exists is restored whole (its absence is not a deletion of every line), and the buffer counts as modified.
- **SAFE-7** [P1][M3] While an external conflict is unresolved, `:w` is refused (`:w!` saves my version). While a proposal is unresolved, `:q` is refused (`:q!` discards) — I, E
  - **Decided** (P1): `:w!` drops the unresolved conflicts from disk, since the disk then holds my version. Proposals from filters stay. The conflicts go when the save is done, not when it is asked for: a save that fails drops nothing, and anything the disk says in the meantime is read again after the answer (PROP-1).
  - **Decided** (P1): `:w`, `:wq`, `:x`, `ZZ` and Ctrl-s (in Insert mode too, which stays Insert mode) are refused while a conflict with the disk is open, with `unresolved conflicts with the disk: ]c to review, :w! keeps yours`, and write nothing. `:w {other}` is allowed: saving mine under another name is how to keep it.
  - **Decided** (P1): `:q`, `q`, `ZZ`, `:x` and `:wq` are refused while any hunk is unresolved, with `unresolved proposals: ]c to review, :q! discards`, which a `:q` says instead of `no write since last change`. A `:wq`, `:x` or `ZZ` that has conflicts with the disk to meet says that first (it is the save that is refused). `:q!`, `ZQ` and `:cq` quit with the hunks open; `:wq!` and `:x!` write by force and quit. Deciding the hunks (PROP-8) or undoing past them opens the door.
  - **Decided** (P1): a `:wq` waits for its save, and is checked again when the save is done: if a hunk is open by then (an undo can bring a rejected one back), the file is saved, the status line says `saved {file}; unresolved proposals: ...`, and si does not quit.
- **SAFE-8** [P1][M1] Control characters (C0, C1, DEL) are shown in `^[` form. Bidirectional controls (U+200E–200F, U+202A–202E, U+2066–2069), U+200B, and U+FEFF anywhere but the start are shown in `<U+202E>` form. None of them is ever sent raw to the terminal (against Trojan Source) — U
  - **Decided** (P2): caret notation has no form for C1, so C1 (U+0080–U+009F) uses the `<U+0085>` form. A tab is shown as spaces (VIS-8).
  - **Decided** (P1): U+061C (Arabic letter mark) is a bidirectional control too, shown the same way.
- **SAFE-9** [P1][M1] Settings and commands are never read from file contents (no modelines). No network access. Tests check that src/ has no `std::net` and that the dependencies match the allowlist — U
  - **Decided** (P1): `signal-hook` is on the allowlist. CLI-4 and SAFE-6 need SIGTERM and SIGHUP without `unsafe`, and crossterm already depends on it, so the binary doesn't grow.

## External changes and Proposals

- **PROP-1** [P1,P2][M3] Watch the parent directory of the open file and take in changes on disk within 100 ms (including saves by rename, deletion and re-creation). Events caused by my own saves are recognized by their hash and ignored — I
  - **Decided** (P1): when the file is deleted, the buffer keeps its text and counts as modified, and the status line says `deleted on disk` (as a note next to `modified`, until the file is saved or comes back). The next `:w` expects no file, so it creates it. If the file comes back from outside, its content is merged like any change on disk.
  - **Decided** (P1): our own save is recognized by the hash of the bytes that were written: the one in flight (the watcher may be quicker than the save thread's answer) and, once it is done, the one of the file as last read or written. Both are ignored, and so is any event whose content hashes like what the buffer already knows. A buffer without a file name is not watched.
  - **Decided** (P1): the App asks for the watch (`Effect::Watch(path)`) whenever it gets a file name (a `:e` that loaded, or the first `:w {file}` of an unnamed buffer); the shell watches the resolved path (symlinks followed), one file at a time, and starts watching before it reads the file at startup so that no change slips in between.
  - **Decided** (P1): the order of a watcher read and a save's answer can't be known, so after every save's answer the file is read once more and taken in like any change (an unchanged file is ignored by its hash). A change seen while the save was in flight is never dropped.
  - **Decided** (P3): that read is the first act of the new watcher's own thread, which also does the debounced reads, so it does not overtake a later read; it reaches App as a normal `Disk` event. The thread also makes the hash of the content (`Disk { hash }`), because hashing 10 MB takes 8 ms (reading it 1 ms) and no key should wait for that; a `Disk` without a hash is hashed by App.
- **PROP-2** [P1,P2][M3] If the buffer is clean, reload it and mark what changed. If it is dirty, run a 3-way merge of base, mine and disk: take in the changes that don't conflict and mark them, and turn the conflicting parts into Proposals. The cursor keeps pointing at the same text — I
  - **Decided** (P1): a reload or a merge is one undo step. Afterwards, the disk content is the new base.
  - **Decided** (P1): the text, the marks and the hunks (PROP-9, PROP-8) are all part of an undo step, so undoing a merge takes its marks and hunks away, redo brings them back, and undoing a reload leaves a buffer that differs from the file, so it counts as modified. The buffer is clean afterwards if and only if its text is the file's.
  - **Decided** (P1): the three texts of the merge all end with a line break, so that a line added at the end is an added line and not a change of the last one. The file's format (BOM, CRLF, final newline) is the one on disk from then on, since that is what a save would replace.
  - **Decided** (P1): the cursor keeps pointing at the same text: its line is carried through the lines that the disk's changes replaced, and its column is kept as far as the line goes. Marks and hunks that exist already are carried the same way: a mark on a line the disk replaced is replaced by the new mark, and a hunk follows its lines and keeps its text. Hunks may overlap when a second change comes in: nothing is dropped.
  - **Decided** (P1): a merge that brings in a different file leaves no older state clean: undoing past it gives a buffer that differs from the file, so it counts as modified. A merge of the file the base already was (recovery) can be undone to clean.
  - **Decided** (P1): a change that cannot be merged is not merged: when the buffer is read-only, or the file is no longer text (SAFE-4), the buffer stays as it is, the status line says `changed on disk, not as text: not merged (:e! reloads, :w! overwrites)`, and the file is not taken as the base, so a save is still refused (SAFE-5).
  - **Decided** (P1): a hunk that comes from a conflict with the disk is marked `disk` (SAFE-7 needs to tell it from a filter's proposal). Its lines are the buffer's lines of mine; `theirs` has its line breaks like every line of the merge. A hunk with no line of mine is an insertion point, or what is left when mine was deleted. A Visual selection ends when a merge comes in, since its anchor is a place in the old text; `'<` and `'>` follow their lines through the merge like the cursor does.
  - **Decided** (P1): undo across a merge that changed the base never makes the buffer clean, since the text then differs from the file. A file that changed only in its format (BOM, CRLF, final newline) counts as a changed base: what a save would write is not what the file holds.
  - **Decided** (P1): a finished save gives the buffer the format it wrote (BOM, CRLF, final newline), whatever a merge took in meanwhile, since the file has that format now. A buffer emptied meanwhile still writes an empty file (SAFE-3).
  - **Decided** (P2): a new conflict whose lines include all the lines of an older conflict with the disk (or, for an older one with no line of mine, its place between two lines) is the disk's newer say on them: it replaces that hunk, so repeated rewrites by an AI do not pile up proposals. One that overlaps only in part leaves both, since the older still offers lines the newer does not (nothing of the disk is dropped, P1). A filter's proposal is never replaced.
  - **Decided** (P2): the view follows a merge like the cursor: the first line on the screen keeps its text, so lines that come in or go above it do not make the screen jump.
  - **Decided** (P2): content that App has taken in already (the watcher's read arrives before the answer of the save that found it) is not merged again, so it makes no undo step that does nothing.
- **PROP-3** [P1][M3] The 3-way merge is our own, built from two `similar` line diffs. Conflict-marker strings are neither generated nor parsed — U
- **PROP-4** [P1][M3] Property: rejecting every hunk gives my version, and accepting every hunk brings in every change from the disk side. No character from either side is lost — U (property test, 10,000 cases)
  - **Decided** (P1): precisely, for a merge of base, mine and theirs: rejecting every hunk gives mine plus the theirs changes that did not conflict (just mine when every theirs change is a proposal, as with filters); accepting every hunk gives the same with theirs winning every conflict (just theirs when mine equals base); until a hunk is resolved, every line of mine and of theirs is either in the buffer or in that hunk.
- **PROP-5** [P3][M4] Filters (`:{range}!cmd`, `!` in Visual mode) run asynchronously with `sh -c`. You can keep working while one runs, and the status line shows the elapsed seconds. Ctrl-c cancels it — I
  - **Decided** (P4): one filter at a time. Ctrl-c stops the filter's whole process group.
  - **Decided** (P5): `:!cmd` without a range filters the current line, as `:s` and `:ref` do, and an empty command is `usage: :{range}!cmd`. The command gets the lines of the range, each followed by a line break (the last one too). A second filter is refused with `a filter is already running (Ctrl-c cancels it)`, and a filter is refused on a read-only buffer, where an accepted proposal would be lost.
  - **Decided** (P1): the buffer under a running filter is never replaced: an `:e` that loads meanwhile is refused with `not opened: a filter is running`. Quitting is not held up: the shell stops the filter then, since nobody is left to read its answer.
  - **Decided** (P3): the status line says `filter 3s · Ctrl-c cancel` after the other notes (VIS-9), counted by the ticks of the shell, which also redraw it, so it can be a second behind. Ctrl-c cancels in Normal mode with `cancelling the filter`; the answer then says `filter cancelled`, and a result that arrives anyway is not taken. In any other mode Ctrl-c does what it always did (Insert, Visual and the command line end). The shell stops the process group off the main thread (`kill` takes a few ms), and a command that cannot be started comes back as an exit code of 127 with the reason in its stderr.
- **PROP-6** [P1,P2][M4] When the filter ends, run a 3-way merge with the buffer at its start as the base, and turn every change from its output into a Proposal (the edits I made meanwhile are kept). With a nonzero exit code, the result is discarded and stderr is shown — I
  - **Decided** (P2): the status line shows the first non-blank line of stderr, or `filter failed (exit 3)` (`killed` for a signal) when there is none.
  - **Decided** (P1): the output is used only if it is text: invalid UTF-8 or a NUL byte discards it with `filter output is not text: discarded`, since a proposal made of U+FFFD would put text in the file that nobody wrote. An output that does not end with a line break gets one, so it cannot run into the line after the range. Empty output is a result (the lines are proposed for deletion). An output equal to the input says `no changes from the filter`.
  - **Decided** (P1, P2): the text of the buffer is not touched and the buffer does not become modified: the proposals join those already open (a filter's or the disk's) in the order of their lines, as one undo step, and `3 proposals from the filter · ]c to review` says so. Edits made meanwhile are in `mine`, so a proposal over a line the user also changed offers the filter's version of the whole block in place of theirs; `n` keeps theirs.
- **PROP-7** [P3][M3] Diffing gives up after 50 ms (the deadline of similar). Even on a 100,000-line file, taking in a change finishes within 50 ms — B
  - **Decided** (P3): the core reads no clock, so the shell stamps the instant with each event that makes a diff (`Disk`, `SaveConflict`, `Recover`): the time it read the content plus 50 ms. Past it a diff is coarse, never wrong: what it could not match counts as changed.
  - **Decided** (P3): word diffs (VIS-2) cost more than their lines are worth on a big rewrite, so one merge looks at 256 KiB of text for words at most. Past that, the lines of a change are painted whole and a hunk has no word diff (every char of mine counts as changed). Measured on 100,000 lines (release): a clean reload, a merge, a rewrite of every line and a conflict over the whole file each take about 20 ms through `App::update`, a frame included. The worst inputs for a diff (every line moved, or the same few lines everywhere) take about 55 ms: the diff gives up at 50 and the rest is linear.
- **PROP-8** [P2,P5][M3] `]c` / `[c` move to the next/previous mark or Proposal. On a Proposal, REVIEW mode starts, and the status line keeps showing `REVIEW 2/5  y accept · n reject · Y all · N none · Esc back`. `y` accepts and `n` rejects, and both move on to the next hunk. `Y` accepts all, `N` rejects all, `Esc` goes back. Each accept is one undo unit — I, E
  - **Decided** (P1): REVIEW starts only when `]c` or `[c` lands on a Proposal, so `y` and `n` never change meaning just because the cursor moved onto a hunk. Inside REVIEW, `]c` and `[c` move on without deciding. Any other key leaves REVIEW and works as in Normal mode. REVIEW ends when no proposal is left.
  - **Decided** (P1): a reject is one undo unit too, so undo brings a rejected hunk back. `Y` and `N` are one undo unit each.
  - **Decided** (P2): `]c` and `[c` go to the nearest mark or hunk in their direction and put the cursor on its first non-blank, centered (VIS-12). In Normal mode a hunk on the cursor's own line counts as the next one (nothing has decided it; a mark there has been seen), so a conflict on line 1 can be reached. In REVIEW the next hunk is the next one in the list. They stop at the ends (`no next change`, `no previous change`), ignore a count (P4), and a mark ends REVIEW. A `]` or `[` that `c` does not follow does nothing, and REVIEW stays.
  - **Decided** (P2): accepting puts the hunk's `theirs` in place of its lines of mine (whatever their place, also at the end of the file or when either side is empty), and the marks on those lines go, since they are decided. The other hunks follow their lines; a hunk that ends where the accepted one starts does not grow over its new lines, for this edit is a decision and not typing next to it. After a decision the cursor goes to the hunk that now has the decided one's place in the list, or the first if it was the last (centered), and when none is left REVIEW ends with `3 proposals accepted` or `rejected`.
  - **Decided** (P2): in REVIEW the status line is the path, `line:col`, `REVIEW i/n` and the keys, cut to the width; a message (such as a refusal, SAFE-7) replaces it until the next key, as everywhere (VIS-9). A paste ends REVIEW and is text (VI-9). Ctrl-s is refused while a conflict is open and leaves REVIEW as it is.
- **PROP-9** [P2][M3] A mark stays until the cursor enters its line. `:seen` clears all of them — I
  - **Decided** (P2): there is one mark per line of the buffer, with the symbol `+` (added), `~` (changed) or `-` (something was deleted just before the line, or after the last line), and the columns of the changed words in it. After every key, the mark of the cursor's line is gone: a motion, a search and a jump all count. A change that arrives while the cursor is on its line keeps its mark until the next key, so that it is seen at least once on the screen.
  - **Decided** (P2): an edit that changes a line takes its mark; lines moved by an edit above them keep theirs. A line that the edit leaves as it was (the one above `o`, the one below `dd`) is not changed. `:seen` clears marks only, never hunks: a hunk is text that nobody has decided about.

  - **Decided** (P2, P4): undo brings back the marks as they were before the undone step, including ones already seen; marks have no identity to remember them by, and showing a change again errs on the safe side. (A list of more than 1,024 marks is the exception, see PERF-2.)
## Look

- **VIS-1** [P2][M1] No syntax highlighting. Text uses only two achromatic levels: primary (|Lc| 90) and secondary (|Lc| 60: line numbers, and unchanged lines during REVIEW) — U
- **VIS-2** [P2][M3] The single chromatic color, "change" (OKLCH h=250), is used only as a background. Changes are painted word by word (a run of letters, digits and `_` is one word; so is each CJK character, and each symbol) — U
- **VIS-3** [P2][M3] Changes are shown without color as well: the gutter shows `+` (added), `~` (changed) and `-` (where something was deleted). During REVIEW, words that would be deleted are struck through in the secondary color — U (golden)
  - **Decided** (P2): the symbol is the first column of the gutter and has the change style itself, so a column of changes can be seen without reading. A deletion point marks the line after it (the last line when the deletion was at the end). A line that is both marked and in a hunk shows `~`; a hunk with no line of mine marks the line after its place, with the symbol only.
  - **Decided** (P2): an edit inside a hunk, or a change from the disk that lands in it, makes its word diff stale, so from then on all of its lines count as changed; an edit elsewhere leaves it.
  - **Decided** (P2): the words of a changed block are found by one word diff over the whole block (old lines against new lines), so a block of many lines is painted as the diff sees it, not line against line.
  - **Decided** (P2): outside REVIEW, a Proposal shows its gutter symbols and puts the change background on the words it would replace. In REVIEW, every hunk is shown inline: inserted words on the change background, deleted words struck through.
  - **Decided** (P2): in REVIEW each hunk is drawn in place of its lines of mine, mine and theirs woven into one text along the word diff: a word of mine that would go is Deleted (secondary, struck through), a word of theirs that would come is on the Change background, a word both have is as it is. A row that only theirs has is an extra row after the row before it, with `+` in the gutter and no number (an empty hunk's rows go before the line after it, or after the last line); a row of a line of mine has `~` and its number. A hunk without a word diff is all struck through with all of theirs as extra rows. The lines nothing changed in (no hunk, no mark) are secondary; marks outside the hunks look as they do outside REVIEW. A hunk too big for the screen is looked at only as far as the screen reaches.
- **VIS-4** [P2][M5] Colors are computed with APCA-W3 0.0.98G-4g from the terminal's background, obtained with OSC 11 (waiting at most 3 ms). Primary text at |Lc| 90, secondary at |Lc| 60, the change background against the normal background at |Lc| ≥ 15, and text on the change background at |Lc| ≥ 75. With no reply, reverse (SGR 7) and faint (SGR 2) stand in; if the reply arrives late, redraw. Checked on every background of `#000000 #1e1e1e #282c34 #002b36 #ffffff #fafafa #fdf6e3 #eff1f5` — U
  - **Decided** (P2): primary and secondary are grays within ±1 of their target Lc. The Lc between the two backgrounds is computed with the change background as the text color.
  - **Decided** (P2): the three numbers cannot hold with one primary gray: 15 + 75 already uses up the 90 between primary and the background once APCA's offset is paid twice (measured: at most 68–72 on the eight backgrounds). So text on the change background gets its own gray, the one closest to primary that keeps |Lc| ≥ 75 there. It stays achromatic (VIS-1): the primary level adjusted to its background, not a new level of meaning.
- **VIS-5** [P2][M5] Even after the color vision deficiency simulation of Machado et al. (2009) for protan, deutan and tritan (severity 1.0), the change background still differs from the normal background by |Lc| ≥ 15 — U
- **VIS-6** [P2][M1] `.md`, `.txt`, `COMMIT_EDITMSG` and files without an extension wrap at 72 columns. Other files wrap at the screen width, and continuation rows show no line number — U
  - **Decided** (P2): 72 columns of text, not counting the gutter; a narrower screen wraps at its own width. A row breaks after a space when it can (and between CJK characters); a word longer than a row is cut at the edge.
  - **Decided** (P2): no row is ever wider than the screen, even on a screen narrower than the gutter plus one wide char or `<U+202E>` token.
- **VIS-7** [P2][M5] Wrapping applies kinsoku: `、。，．）」』】〕〉》ー…‥・！？` never start a row, and `（「『【〔〈《` never end one. A full-width character counts as 2 columns (unicode-width) — U (property test)
  - **Decided** (P2): when a row cannot satisfy kinsoku (a row of nothing but `、`), it breaks at the edge anyway.
  - **Decided** (P2): an emoji presentation sequence (a char followed by U+FE0F) takes 2 columns and a ZWJ sequence counts as one cluster, as grapheme-clustering terminals (Ghostty, kitty, WezTerm) draw them.
  - **Decided** (P2): a blank is never widened by U+FE0F. A ZWJ joins only an emoji to an emoji: before the ZWJ a wide pictograph, or a narrow one with its U+FE0F; after it a wide pictograph, or a narrow one followed by U+FE0F. `a` + ZWJ + `b` are three plain chars. That never reads narrower than `unicode-width` does a string (checked on every string of up to 6 chars over a few emoji, CJK, blanks, U+FE0F and ZWJ). A U+FE0F that follows a `^[` or `<U+202E>` token, or another U+FE0F, is not sent, since the terminal would widen the token's last char.
- **VIS-8** [P2][M1] A tab is displayed as 4 columns — U
  - **Decided** (P2): tab stops are every 4 columns, so text aligned with tabs stays aligned.
- **VIS-9** [P2][M1] State is shown in words. The status line has the form `path  line:col  MODE  modified · 3 changes on disk · 2 proposals` — U (golden)
  - **Decided** (P2): MODE is NORMAL, INSERT, VISUAL, V-LINE or REVIEW, and col counts characters from 1. Parts that don't apply are left out, and a count of one is singular. Other states (read-only with its reason, `deleted on disk`, a running filter) are added the same way, in the order: modified, read-only, deleted on disk, changes on disk, proposals, filter. A change on disk is a run of marked lines next to each other (a block of ten added lines is one change); a proposal is a hunk. A message (an error, `search wrapped`) replaces the status line until the next key. While typing after `:`, `/` or `?`, the status line is the command line. An unnamed buffer shows `[no name]`.
- **VIS-10** [P2][M1] The cursor shape also shows the mode (Normal: block, Insert: bar, REVIEW: underline; none of them blink). Checked through the DECSCUSR output — U
  - **Decided** (P5): Visual mode uses the block, and the command line uses the bar.
  - **Decided** (P2): REVIEW's underline (DECSCUSR 4, steady) is drawn at the start of the first row of the hunk the status line names.
- **VIS-11** [P4][M1] No decoration: no icons, no box drawing, no `~` past the end of the file, no highlighting of the cursor line — U (golden)
  - **Decided** (P2): the cursor line's number is drawn in the primary gray and the other numbers in the secondary: a cue to where the cursor is, not a highlighted bar (`cursorlineopt=number` in the author's nvim, for the same reason).
- **VIS-12** [P2][M1] The eyes find their place again: `n N * # ]c [c Ctrl-d Ctrl-u`, `:N`, `+N` and `file:line` put the cursor line in the middle of the screen, and moving the cursor keeps at least 8 lines of context above and below it (half the text area on a short screen) — U
  - **Decided** (P2): centering applies near the end of the file too; rows past the last line stay blank.

  - **Decided** (P2): a line taller than the screen scrolls by rows, so the cursor stays visible inside it.
## Keys

The vi grammar the hands already know, departing from vi wherever vi is worse than modern editors (P5).

- **VI-1** [P5][M1] Motions: `h j k l w b e W B E 0 ^ $ gg G f F t T ; , % Ctrl-d Ctrl-u zz`. A count can be given — U
  - **Decided** (P4): `%`, `n`/`N` and text objects ignore counts; `%` matches `()[]{}` only. `n N * #` are motions, so `dn` works, but an operator followed by `/` is cancelled (no `d/re`).
  - **Decided** (P5): word motions split CJK text where the script changes (Han, Hiragana, Katakana, and other wide characters are classes of their own), as in vim. vim's `:help exclusive` rules apply: an exclusive motion that ends in column 1 ends at the end of the line before, and becomes linewise if it started at or before the first non-blank (so `dw` on an empty line deletes it).
  - **Decided** (P5): `cw` on an empty line, and a `dw` that starts on one, end at the start of the next line, not at its first word (vim's `fwd_word` stops there). vim's `:help d` rule that makes a multi-line delete linewise is not taken (P4).
- **VI-2** [P5][M1] Editing: `x r J p P u Ctrl-r . i a I A o O dd cc yy D C Y >> <<` — U
  - **Decided** (P5): `Y` yanks to the end of the line, consistent with `D` and `C` (Neovim's default; vi's `Y` duplicates `yy`). `U` redoes, like Ctrl-r (vi's line-undo `U` is dropped). `>>` and `<<` shift by the indent unit of VI-6.
  - **Decided** (P5): `.` replays the keys of the last Normal-mode change, a new count replacing the old one; Visual-mode operations are not repeated, and a replay stops at the first key that fails. A paste inside an insert session belongs to that session's undo unit. After undo the cursor goes back to where it was before the command. A `.` among the keys of a replay does nothing, so a replay can never run for ever.
  - **Decided** (P1): counts saturate instead of overflowing, motions stop at the ends of the text, and a command that would produce more than 16 MiB of text (a held-down count on `p` or `r`) is refused with a message: the largest file si is specified for is 10 MB (PERF-5), and an allocation far beyond it could abort the editor and lose the buffer. `.` after `u` repeats the last change, not the undo. `J` adds no space before a `)`. The message is `too large: 16 MiB at most`; the limit is on what the command adds.
- **VI-3** [P5][M1] The operators `d c y > < !` combine with a motion or a text object (`iw aw iW aW i" a" i' a' i( a( i[ a[ i{ a{ i< a<`) — U
  - **Decided** (P5): `!{motion}` opens the command line with `:{range}!`, as in vi.
- **VI-4** [P5][M1] Search: `/ ? n N * #`. Regular expressions use the syntax of regex-lite — U
  - **Decided** (P2, P5): a search wraps around the end of the file with the message `search wrapped`. It is smartcase: a pattern without an uppercase letter ignores case, one with an uppercase letter doesn't. `*` and `#` search for the whole word under the cursor, case-sensitively. Matches are not highlighted, since color is only for change.
  - **Decided** (P4): `*` and `#` put `\b` only at ASCII word edges (regex-lite's `\b` is ASCII-only). Matches never overlap.
  - **Decided** (P4): smartcase looks at letters only, not at escapes such as `\W`, and folds ASCII letters only (regex-lite's `(?i)`).
- **VI-5** [P5][M1] Visual mode: `v V o`. It takes the same operators as VI-3 — U
  - **Decided** (P2): the selection is shown with an underline (SGR 4), because color is reserved for change and reverse video is the fallback for change (VIS-4). `:` in Visual mode starts the command line with `'<,'>`.
  - **Decided** (P4): Visual mode takes motions, text objects, `o`, the operators and `:`; other Normal-mode commands (`p`, `J`, `u`, `.`, `/`) do nothing there. A text object widens a selection longer than one char.
- **VI-6** [P5][M1] Insert mode: typing, BS, Enter (keeps the indent of the line above), Tab (inferred from the file: a tab if the first indented line uses a tab, that many spaces if it uses spaces, otherwise 4 spaces), Ctrl-w, Ctrl-u, Esc — U
  - **Decided** (P5): BS at the start of a line joins it to the line above.
  - **Decided** (P5): Ctrl-[ and Ctrl-c leave Insert mode like Esc, since the hands know both. Moving with the arrows inside one insert session keeps it one undo unit.
  - **Decided** (P2): an indent that nothing was typed after is removed again when Insert mode ends or the line is left, so `o<Esc>` leaves no trailing blanks.
  - **Decided** (P2): it is the indent of `o`, `O`, Enter and `cc` that counts. A char or Tab typed on the line makes it text; BS, arrows within the line and the like do not.
- **VI-7** [P5][M1] ex commands: `:w [file]` `:w!` `:q` `:q!` `:wq` `:x` `:cq` `:e {file}` `:e!` `:{N}` `:{range}s/re/rep/[g]` `:{range}!cmd` `:seen` `:ref`. Ranges are `N` `N,M` `%` `.` `$` `'<,'>` — U
  - **Decided** (P5): `:q` and `:e {file}` are refused while the buffer is modified (`:q!` and `:e!` discard). In the replacement of `:s`, `&` and `\1`–`\9` refer to the match, as in vi. `:x` writes only when the buffer is modified.
  - **Decided** (P1): a file arrives as an event, so the buffer may be edited between `:e` and the arrival. The App records the buffer's version when the command runs, and if it differs when the file arrives (an edit that was undone again gives the same version), it refuses the load with `not opened: edited meanwhile` instead of discarding those edits.
  - **Decided** (P4, P5): ranges have no `+N` offsets; `N,M` with M < N is swapped, numbers clamp to the file, and a bare range goes to its last line. `:e` without a file reloads (refused while modified); `:wq!` and `:x!` force the write. `:s` takes only the `g` flag, and `:s//rep/` reuses the last search pattern.
  - **Decided** (P1, P2): a range that doesn't parse is an error, never ignored. `:w !cmd` is refused (filters are `:{range}!cmd`). `:wq {other}` and `:x {other}` write the other file and don't quit while the buffer's own file still differs, and say so.
  - **Decided** (P1): `:w` is refused while an `:e` is still reading, an `Opened` nobody asked for is ignored, and every `:e` keeps its own expected version, so two quick `:e!` can't discard the edits made between them. When one of them loads, the next answer is checked against the new buffer as it was loaded (versions start again at 0): it loads only if nothing was typed since.
- **VI-8** [P5][M1] There is only one register, with no register names. Every yank also sends the text to the system clipboard through OSC 52; a delete or a change fills only the register — U
  - Changed from "a yank prefixed with `"+`": copying out to another program is the common case, and a prefix to remember costs keys without adding safety (P5). Deletes stay out of the clipboard so that `x` and `dd` never clobber what you copied.
  - **Decided** (P2): inside tmux (`$TMUX` set) the sequence is also sent wrapped in tmux's passthrough, because tmux's default `set-clipboard external` drops it.
  - **Decided** (P2): a delete or yank of nothing leaves the register and the clipboard alone; `p` with an empty register says so.
  - **Decided** (P2): the message is `the register is empty`.
  - **Decided** (P2): a yank says what it took (`3 lines yanked`, `12 chars yanked`), since the clipboard gives no other sign (the author's nvim flashes the yanked text; si has no color to spare).
- **VI-9** [P3][M1] The kitty keyboard protocol is enabled without waiting for a query. Esc is handled without delay. Bracketed paste is enabled, and one paste is one undo unit — U
  - **Decided** (P1): a paste is always inserted at the cursor as text and never run as keys, whatever the mode (Visual and REVIEW end first). On the command line, line breaks in a paste become spaces.
  - **Decided** (P1): without the kitty protocol (in tmux, over ssh), Esc and the next key can arrive together and look like Alt+key. si has no Alt bindings, so Alt+key is read as Esc, then the key. A paste also ends a pending count or operator.
  - **Decided** (P5): a paste is text, not keys, so `.` does not repeat it: the change that `.` repeats is the keys that were typed.
- **VI-10** [P2,P5][M4] In Normal mode, full-width ASCII (U+FF01–FF5E) is read as half-width (so you can keep operating with the IME on) — U
  - **Decided** (P5): this applies to command keys in Normal, Visual and REVIEW mode and after an operator, but not to the character after `f F t T r`, nor in Insert mode or on the command line.
  - **Decided** (P5): the range is exactly U+FF01–FF5E, each read as the ASCII char 0xFEE0 below it. The ideographic space (U+3000) and the half-width forms next to the range are not read as anything.
- **VI-11** [P2][M4] If the environment variable `SI_ON_NORMAL` is set, it runs asynchronously with `sh -c` every time Normal mode is entered (e.g. `fcitx5-remote -c` to turn the IME off) — I
  - **Decided** (P2): it also runs once at startup, since si starts in Normal mode.
  - **Decided** (P2): an entry is a change of mode to Normal from Insert, Visual, the command line or REVIEW (leaving REVIEW with its last decision, with Esc or another key, or with a paste). Esc in Normal mode and the motions are not entries, and nothing runs on the way out. An empty `SI_ON_NORMAL` counts as unset.
  - **Decided** (P1, P3): the shell runs it with `sh -c` in its own process group, with no input, reaps it from a thread, and drops its output and its failure: a hook can never block a key or write on the screen.
- **VI-12** [P5][M1] The keys every editor has work everywhere: the arrows, Home, End, PageUp, PageDown and Delete in Normal, Visual and Insert mode, and Left, Right, Home, End, BS and Delete on the command line — U
  - **Decided** (P2): a command line longer than the screen scrolls to keep its cursor visible.
  - **Decided** (P2): it keeps the scroll it has while the cursor stays on the screen, and always the char before the cursor, so Home shows the start again.
- **VI-13** [P5][M1] Finishing takes few keys: Ctrl-s saves in every mode (Insert mode stays Insert mode); `ZZ` saves if modified and quits, like `:x`; `ZQ` quits without saving, like `:q!`; `q` quits like `:q` (as in less; si has no macros). Ctrl-c with nothing to cancel says `q to quit` — U

- **VI-14** [P2][M4] Incremental search: while a `/` or `?` pattern is typed, the cursor jumps to the first match from where the search started (centered, VIS-12); Esc goes back there. Nothing is highlighted — U
  - From the author's nvim (`incsearch`, the default in vim 9 and Neovim): you see where you are going before Enter.
  - **Decided** (P2 over P3): on a 100,000-line file a key of the search line may take up to PERF-4's 50 ms, since it is a search (the line itself, `n`, and Enter cost the same). No other key is allowed this. The status line is the command line, so the search is the one thing on the screen that moves.
  - **Decided** (P1, P2): the cursor itself does not move while the line is typed: the screen is drawn around the first match as if it were there (centered, VIS-12; the number of that line is the cursor line's), and Enter then moves the cursor by searching as it always does, so the two cannot differ. Esc, and the Backspace that removes the `/`, have nothing to give back, a change that arrives from the disk meanwhile cannot leave the cursor or the view anywhere but where the search started, and the marks of PROP-9 stay on the lines the preview passes (a mark goes when the cursor enters its line; one that is shown for a moment and then gone unseen would defeat it). Each key searches again from the cursor; a pattern that is empty, does not compile, or matches nothing shows the cursor's own place, and the last search (`n`) is not touched.
## The AI era

- **AI-1** [P2][M4] `:ref` sends `path:start-end` (relative to the current directory) to the clipboard through OSC 52, to hand a location to an agent. In Visual mode it uses the selection; in Normal mode, the current line — I
  - **Decided** (P5): `:ref` takes a range like the other ex commands, so it is `:'<,'>ref` from Visual mode. A file outside the current directory is given by its absolute path.
  - **Decided** (P5): the form is always `path:start-end`, also for one line (`a.rs:5-5`), so that whoever reads it needs one pattern. Lines count from 1. The directory is the shell's `current_dir`, and the path is made relative lexically (`.` and `..` resolved, no symlinks looked at); `/work/../tmp/a` from `/work` is `/tmp/a`. `:ref` does not fill the register. ## Performance (measured on a release build)

- **PERF-1** [P3][M1] `si +q` opens and closes a 10,000-line file within 5 ms (median of hyperfine) — B
  - **Decided** (P3): si needs a terminal, so `scripts/bench.sh` runs hyperfine inside a private tmux when it is installed. Otherwise `scripts/pty_bench.py` spawns the release binary in a pty; the median it reports includes starting the process from Python, and the test (`perf_1_bench_startup_under_5ms`) asserts that raw median, so it is stricter than hyperfine's.
- **PERF-2** [P3][M1] On a 100,000-line file, handling one key (motion, insert, delete, undo) and building the Frame take at most 1 ms at p99 — B
  - **Decided** (P3): the time of a key is `App::update` plus `Term::draw` into memory, i.e. everything before the write to the terminal, measured on 80x24 and 240x60 screens.
  - **Decided** (P3): marks and hunks are shared with the undo steps, and an edit that moves them copies the list as counts and pointers, never as clones of their words and text (a mark that paints its whole line holds no words at all). Measured on 100,000 lines after a rewrite of every line (100,000 marks, release): an edit that moves the marks takes about 0.2 ms through `App::update` (2.5 ms when every mark was cloned), a key that does not about 0.1 ms; 3,000 hunks cost the slowest key 0.2 ms. Every such edit copies the list, so a list of more than 1,024 marks is kept by the last 4 undo steps only (16 copies of 100,000 marks, 3 MB each, fall out of the cache and cost 160 µs against 70 µs for 4, and a session of edits would hold gigabytes); undo further back does not bring those marks back. Hunks are never let go (P1).
- **PERF-3** [P3][M1] After one character is inserted, only that line is sent to the terminal again — U (bytes written)
  - **Decided** (P2): plus the status line, whose `line:col` changed, and the cursor position.
  - **Decided** (P3): a frame that rewrites anything is wrapped in synchronized output (`CSI ? 2026 h` … `CSI ? 2026 l`), so a terminal that supports it never shows half of a frame; terminals that don't know it ignore it. A frame that only moves the cursor is sent as it is.
- **PERF-4** [P3][M1] On a 100,000-line file, a search that matches nothing (the worst case) finishes within 50 ms — B
  - **Decided** (P3): a line that lacks a literal the pattern requires (the longest plain run, e.g. `foo` in `foo\d+bar`) is skipped without running the regex, because regex-lite does about 20 ns a byte and a 100,000-line file is several MB.
  - **Decided** (P3): regex-lite stays, and the worst case is held by running it in parallel. A buffer of 512 KiB or more is searched in 8 chunks of lines (a fixed number, so the result never depends on the machine) on `std::thread::scope` threads that only read the text; the first chunk in search order that has a match wins, so the match is exactly the one a single thread finds. The first 256 lines run on one thread before any starts, so a match near the cursor costs no thread. 8 threads bring a regex with no useful literal on 7.65 MB from about 150 ms to about 24 ms, on a machine with 8 or more cores.
- **PERF-5** [P4][M1] The release binary is at most 2 MB (strip, LTO). With a 10 MB file open, RSS is at most 50 MB — B
  - **Decided** (P4): the test asserts the peak (VmHWM) after the first frame, which is never lower than the RSS at that moment. It runs on Linux only.
